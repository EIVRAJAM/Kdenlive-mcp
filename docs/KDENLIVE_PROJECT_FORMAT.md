# Kdenlive Project Format Reconnaissance

Date: 2026-08-14

## Status

The `.kdenlive` project format has not yet been reverse-engineered for this
installation because no real `.kdenlive` file generated by Kdenlive 26.04.3 was
available during this reconnaissance pass.

This is intentional: the project must not write Kdenlive XML based on guesses.
The only XML generated in this phase is plain MLT XML from `melt`, stored at:

```text
examples/recon/sample_mlt.xml
```

That file is useful for MLT validation, but it is not sufficient to define a
safe `.kdenlive` writer.

## Verified MLT Shape

`examples/recon/sample_mlt.xml` was generated with Kdenlive Flatpak's own
`melt 7.40.0` using the `vertical_hd_30` profile.

The top-level structure is:

```text
mlt
  profile
  producer
  producer
  playlist
    entry
    entry
  tractor
    track
```

Observed details:

```text
Root element: <mlt>
MLT version: 7.40.0
Profile: Vertical HD 30 fps, 1080x1920, 30 fps, 9:16
Producer service: avformat
Producer resources: examples/recon/sample1.mp4 and sample_vertical.mp4
Timeline sequence: one playlist with two entries
Tractor: one track referencing that playlist
Time unit in generated XML: frame indices for in/out on producers and entries
```

Example timing from the generated file:

```text
sample1.mp4: 90 frames, producer in=0, out=89
sample_vertical.mp4: 90 frames, producer in=0, out=89
tractor out=179
```

This supports the internal design decision to use integer frames as the core
timeline unit and convert to seconds/timecode at service boundaries.

## What Remains Unknown For `.kdenlive`

The following Kdenlive-specific structures still require a real project saved by
Kdenlive 26.04.3:

```text
Project bin metadata
Kdenlive document properties
Stable clip IDs
Folder/bin IDs
Track metadata
Audio/video target track mapping
Track names, lock state, mute state
Timeline playlists generated by Kdenlive
Kdenlive-specific producer properties
Markers and guides
Effects and effect stack metadata
Transitions/compositions
Proxy references
Sequence metadata
Subtitle track representation
Autosave and backup conventions
```

Plain MLT XML shows the MLT base, but Kdenlive adds application-specific
properties. Those properties must be isolated behind a `KdenliveProjectAdapter`
and tested through round-trips with Kdenlive.

## Manual Project Capture Needed

Before implementing `create_project`, `import_media`, or timeline mutation, make
one minimal project manually in Kdenlive 26.04.3:

```bash
flatpak run org.kde.kdenlive
```

Recommended manual steps:

```text
1. Create a new project using profile Vertical HD 30 fps.
2. Save it as examples/recon/manual_empty_vertical.kdenlive.
3. Import examples/recon/sample1.mp4 and examples/recon/sample_vertical.mp4.
4. Save as examples/recon/manual_bin_only.kdenlive.
5. Add both clips sequentially to the timeline.
6. Save as examples/recon/manual_two_clips_timeline.kdenlive.
7. Trim the first clip and add one marker/guide if convenient.
8. Save as examples/recon/manual_trim_marker.kdenlive.
```

Then run:

```bash
xmllint --noout examples/recon/manual_empty_vertical.kdenlive
xmllint --noout examples/recon/manual_bin_only.kdenlive
xmllint --noout examples/recon/manual_two_clips_timeline.kdenlive
xmllint --noout examples/recon/manual_trim_marker.kdenlive

flatpak run --command=melt org.kde.kdenlive \
  examples/recon/manual_two_clips_timeline.kdenlive \
  -consumer null
```

After those files exist, compare them structurally:

```bash
diff -u \
  examples/recon/manual_empty_vertical.kdenlive \
  examples/recon/manual_bin_only.kdenlive

diff -u \
  examples/recon/manual_bin_only.kdenlive \
  examples/recon/manual_two_clips_timeline.kdenlive
```

The diffs should be used to document:

```text
How Kdenlive stores bin clips
How Kdenlive names producers/playlists/tractors
Which properties are required versus derived
How timeline entries map to bin producers
How frame in/out points are represented
Which fields change on save even without semantic edits
```

## Attempted Non-Manual Capture

Kdenlive was launched with `-i` and the synthetic clips to test whether a target
`.kdenlive` argument would be created automatically. It was not.

Kdenlive DBus was also inspected. The application exposes generic KXMLGui
actions and Kdenlive-specific methods, including:

```text
org.kde.KMainWindow.activateAction(file_save)
org.kde.KMainWindow.activateAction(file_save_as)
org.kde.kdenlive.MainWindow.addProjectClip(url)
org.kde.kdenlive.MainWindow.addTimelineClip(url)
org.kde.kdenlive.MainWindow.updateProjectPath(path)
```

`file_save` opens a modal GUI save dialog when the project has no real document
path. `updateProjectPath(path)` did not assign a real save path for the current
document. Therefore, DBus did not provide a safe headless way to generate the
reference `.kdenlive` files.

This reinforces the current rule: obtain real `.kdenlive` samples through
Kdenlive's own save operation before implementing a writer.

## Adapter Boundary Decision

All `.kdenlive` handling should live behind:

```text
TimelineService
  -> KdenliveProjectAdapter
    -> XML / MLT
```

The domain model should not read or write XML directly. The adapter should own:

```text
XML parsing
XML serialization
Kdenlive-specific property names
MLT profile mapping
Producer and playlist ID allocation
Round-trip preservation of unknown properties
Compatibility checks against Kdenlive 26.04.3
```

## Initial Technical Decisions

Use integer frames as the canonical timeline unit.

Preserve unknown XML nodes and properties during edits. Kdenlive can add fields
that are not relevant to the MCP operation but still required for a clean
round-trip.

Use Flatpak `melt` as the project-load validation tool when Kdenlive GUI loading
cannot be automated.

Treat host `ffprobe` as acceptable for fast media scanning, but compare critical
metadata with Flatpak `ffprobe` before project generation or render.

Do not implement `.kdenlive` writing until at least the four manual reference
projects above exist and have been compared.
