# Kdenlive Project Format Reconnaissance

Date: 2026-08-19

Kdenlive project writing must be based on real projects generated by the
installed Kdenlive version, not on guessed XML. This document records the first
confirmed structure from Kdenlive 26.04.3 Flatpak with MLT 7.40.0.

## Reference Files

Captured manually through Kdenlive 26.04.3:

```text
examples/recon/manual_empty_vertical.kdenlive
examples/recon/manual_bin_only.kdenlive
examples/recon/manual_two_clips_timeline.kdenlive
examples/recon/manual_trim_marker.kdenlive
```

All four files are well-formed XML and load through the Flatpak `melt` binary:

```bash
xmllint --noout \
  examples/recon/manual_empty_vertical.kdenlive \
  examples/recon/manual_bin_only.kdenlive \
  examples/recon/manual_two_clips_timeline.kdenlive \
  examples/recon/manual_trim_marker.kdenlive

flatpak run --command=melt org.kde.kdenlive \
  examples/recon/manual_two_clips_timeline.kdenlive \
  -consumer null terminate_on_pause=1
```

Kdenlive also created a cache folder named after the document id:

```text
examples/recon/1787190383242/
```

That folder contains thumbnails and audio thumbnails. It is not part of the
canonical project file and is ignored by Git.

## Top-Level Shape

The `.kdenlive` file is MLT XML with Kdenlive-specific properties:

```text
mlt
  profile
  producer
  chain
  playlist
  tractor
```

Observed root attributes:

```text
LC_NUMERIC="C"
producer="main_bin"
root="/data/PROYECTOS/kdenlive-mcp/examples/recon"
version="7.40.0"
```

The project profile for the captured files is:

```text
description: Vertical HD 30 fps
width: 1080
height: 1920
frame_rate_num: 30
frame_rate_den: 1
display_aspect_num: 9
display_aspect_den: 16
progressive: 1
colorspace: 709
```

This confirms that `vertical_hd_30` is the correct preset base for the initial
9:16 MVP.

## Document Properties

Project-level Kdenlive metadata is stored as properties on:

```text
<playlist id="main_bin">
```

Important observed properties:

```text
kdenlive:docproperties.kdenliveversion = 26.04.3
kdenlive:docproperties.version = 1.1
kdenlive:docproperties.profile = vertical_hd_30
kdenlive:docproperties.documentid = 1787190383242
kdenlive:docproperties.storagefolder = 1787190383242
kdenlive:docproperties.uuid = {6a35fbbe-4823-4d58-8e13-31c36ec1ef29}
kdenlive:docproperties.activetimeline = {6a35fbbe-4823-4d58-8e13-31c36ec1ef29}
kdenlive:docproperties.opensequences = {6a35fbbe-4823-4d58-8e13-31c36ec1ef29}
kdenlive:docproperties.enableproxy = 0
kdenlive:docproperties.generateproxy = 0
```

Decision: the adapter must preserve unknown `kdenlive:docproperties.*` values
during round trips. It should only modify properties it owns or has explicit
tests for.

## Project Bin

The root `mlt` points to `main_bin`:

```text
<mlt producer="main_bin" ...>
```

`main_bin` contains entries for the active sequence and imported media:

```text
manual_empty_vertical:
  tractor4

manual_bin_only:
  tractor4
  chain0 -> sample_vertical.mp4
  chain1 -> sample1.mp4

manual_two_clips_timeline:
  tractor4
  chain4 -> sample_vertical.mp4
  chain5 -> sample1.mp4
```

Media clips are represented as `<chain>` elements using:

```text
mlt_service = avformat-novalidate
resource = sample1.mp4
kdenlive:id = 5
kdenlive:folderid = -1
kdenlive:clip_type = 0
kdenlive:file_size = ...
kdenlive:file_hash = ...
kdenlive:control_uuid = {...}
```

The observed media resources are relative to the project root:

```text
sample1.mp4
sample_vertical.mp4
```

Decision: initial project creation should prefer relative paths when media is
inside the project root, while still keeping source files untouched.

## Sequences And Project Tractor

The captured project contains one sequence:

```text
tractor4
```

Observed sequence properties:

```text
kdenlive:clipname = Secuencia 1
kdenlive:id = 3
kdenlive:producer_type = 17
kdenlive:duration = 00:00:06.000
kdenlive:maxduration = 180
kdenlive:sequenceproperties.tracksCount = 4
kdenlive:sequenceproperties.videoTarget = 2
kdenlive:sequenceproperties.audioTarget = 1
```

The project-level tractor references the sequence:

```text
<tractor id="tractor5" in="00:00:00.000" out="00:00:05.967">
  <property name="kdenlive:projectTractor">1</property>
  <track producer="tractor4" in="00:00:00.000" out="00:00:05.967"/>
</tractor>
```

Decision: the adapter needs to model the active sequence separately from the
root project tractor. Timeline edits should target the active sequence tractor,
not `main_bin` and not the project tractor directly.

## Tracks And Playlists

The empty vertical project has four user tracks represented as nested tractors:

```text
tractor0 -> playlist0, playlist1   audio track pair
tractor1 -> playlist2, playlist3   audio track pair
tractor2 -> playlist4, playlist5   video track pair
tractor3 -> playlist6, playlist7   video track pair
```

The active sequence tractor references them with a black background producer:

```text
tractor4
  track producer="producer0"
  track producer="tractor0"
  track producer="tractor1"
  track producer="tractor2"
  track producer="tractor3"
```

Audio track playlists include:

```text
<property name="kdenlive:audio_track">1</property>
```

Video track playlists do not include that property. Track visibility is encoded
inside the nested track references:

```text
hide="video" for audio-only track branches
hide="audio" for video-only track branches
```

Decision: track creation/removal is higher risk than simple clip insertion
because it affects paired playlists, nested tractors, transitions, target track
properties, and sequence track count metadata.

## Timeline Entries

For the two-clip timeline sample, the same two source media items are present in
audio and video playlists:

```text
playlist0 audio:
  entry producer="chain0" in="00:00:00.000" out="00:00:02.967"
    kdenlive:id = 4
  entry producer="chain1" in="00:00:00.000" out="00:00:02.967"
    kdenlive:id = 5

playlist6 video:
  entry producer="chain2" in="00:00:00.000" out="00:00:02.967"
    kdenlive:id = 4
  entry producer="chain3" in="00:00:00.000" out="00:00:02.967"
    kdenlive:id = 5
```

Important observation: Kdenlive does not reuse the exact same `chain` element
for bin, audio timeline, and video timeline. It created separate chains that
share the same Kdenlive media id and resource:

```text
chain0 / chain2 / chain4 -> sample_vertical.mp4, kdenlive:id 4
chain1 / chain3 / chain5 -> sample1.mp4, kdenlive:id 5
```

Decision: stable domain media IDs must not be equated with MLT XML element IDs.
The future adapter needs an allocation strategy for XML ids and a separate
mapping for Kdenlive clip ids.

## Groups

Audio/video linked clip groups are stored as JSON in:

```text
kdenlive:sequenceproperties.groups
```

Observed shape:

```json
[
  {
    "children": [
      {"data": "3:0:-1", "leaf": "clip", "type": "Leaf"},
      {"data": "0:0:-1", "leaf": "clip", "type": "Leaf"}
    ],
    "type": "AVSplit"
  }
]
```

The first number in `data` appears to reference the track index and the second
number the timeline position in frames. This is an inference from the two
observed groups:

```text
3:0:-1 and 0:0:-1
3:90:-1 and 0:90:-1
```

Decision: group JSON must be treated as Kdenlive-owned until additional samples
confirm the exact semantics. Clip insertion can initially avoid complex group
editing or update it only through tested helper methods.

## Guides And Markers

The `manual_trim_marker.kdenlive` sample contains a guide/marker named `hook`:

```json
[
  {
    "comment": "hook",
    "duration": 75,
    "pos": 0,
    "type": 0
  }
]
```

It appears in both:

```text
kdenlive:sequenceproperties.guides
kdenlive:markers
```

Decision: marker/guide support should be implemented as a small, isolated
adapter feature after basic sequence parsing exists.

## Trims

The file named `manual_trim_marker.kdenlive` contains the marker, but the saved
timeline entries still match `manual_two_clips_timeline.kdenlive`:

```text
in = 00:00:00.000
out = 00:00:02.967
```

Therefore this sample does not yet prove Kdenlive's trim representation. A new
reference file is still needed where a clip is visibly trimmed and saved.

Required next trim sample:

```text
examples/recon/manual_trimmed_clip.kdenlive
```

Recommended manual action: trim the first clip so its source in-point is not
zero and save a separate file.

## Time Representation

The captured `.kdenlive` files use time strings like:

```text
00:00:00.000
00:00:02.967
00:00:05.967
```

At 30 fps, 90 frames are represented by roughly 2.967 seconds when `out` is
inclusive. The sequence duration is separately stored as:

```text
kdenlive:duration = 00:00:06.000
kdenlive:maxduration = 180
```

Decision: the domain model should keep integer frames as the canonical unit and
convert to Kdenlive/MLT time strings only at the adapter boundary.

## Transitions

Each empty sequence already has default transitions/compositions:

```text
transition0 mlt_service=mix     a_track=0 b_track=1
transition1 mlt_service=mix     a_track=0 b_track=2
transition2 mlt_service=qtblend a_track=0 b_track=3
transition3 mlt_service=qtblend a_track=0 b_track=4
```

Decision: default transitions should be preserved when writing a project. The
first MVP should not attempt to create arbitrary effects/transitions until
project round-trip behavior is proven.

## Adapter Boundary Decision

All `.kdenlive` handling must live behind:

```text
TimelineService
  -> KdenliveProjectAdapter
    -> XML / MLT
```

The adapter should own:

```text
XML parsing
XML serialization
Kdenlive-specific property names
MLT profile mapping
Sequence detection
Main bin parsing
Producer/chain/playlist/tractor id allocation
Unknown property preservation
Compatibility validation through xmllint and Flatpak melt
```

The domain model must not manipulate XML nodes directly.

## Remaining Unknowns

Still not confirmed enough for writing:

```text
Trimmed clip source in/out representation
Timeline blanks/gaps after moving clips
Track rename, lock, mute, and height metadata
Explicit folder/bin nesting beyond the default sequence folder
Proxy attachment fields
Subtitle track representation
Effect stack representation
Fade and dissolve representation
Kdenlive behavior after round-tripping an AI-written project
```

## Current Write Boundary

The project now has an experimental `export_timeline_to_mlt_xml` path that
converts the MCP-owned timeline JSON into a minimal MLT XML draft:

```text
kdenlive_mcp_timeline
  -> MLT XML draft
```

This is intentionally not a `.kdenlive` writer. It does not attempt to preserve
Kdenlive document properties, `main_bin`, sequence UUIDs, nested Kdenlive track
tractors, groups, guides, effects, proxies, or project-bin metadata.

Validation note: a generated draft under `examples/recon` loaded successfully
with:

```bash
flatpak run --command=melt org.kde.kdenlive \
  examples/recon/codex_mlt_export.mlt.xml \
  -consumer null terminate_on_pause=1
```

The same generated XML under `/tmp` failed to load from Flatpak in this local
environment, while the workspace copy succeeded. Treat that as a Flatpak
filesystem-scope constraint when choosing output directories for manual tests.

The project also has a first template-based `.kdenlive` draft writer:

```text
kdenlive_mcp_timeline
  -> manual_empty_vertical.kdenlive copy
  -> filled playlist0 / playlist6 entries
  -> derived .kdenlive draft
```

Validation note: a generated `.kdenlive` draft under `examples/recon` loaded
successfully with:

```bash
flatpak run --command=melt org.kde.kdenlive \
  examples/recon/codex_kdenlive_export.kdenlive \
  -consumer null terminate_on_pause=1
```

Current limitations: the writer targets the observed `playlist0` audio track
and `playlist6` video track only. It does not yet support multiple editable
tracks, effects, transitions, subtitles, proxies, or full Kdenlive project
metadata regeneration.
